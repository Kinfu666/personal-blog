## schema 裡有外鍵，仍要驗證連線

SQLite 的外鍵檢查需要對每條連線啟用。即使建表 SQL 宣告 `REFERENCES`，未啟用的連線仍可能寫入不存在的分類 ID。連線池讓這件事更容易被忽略：手動執行一次 PRAGMA，可能只影響當時借到的那一條連線。

![資料庫圖示]({{image:database}})

```sql
PRAGMA foreign_keys = ON;
PRAGMA busy_timeout = 5000;
PRAGMA foreign_key_check;
```

正式程式應透過 SQLite JDBC 的連線設定保證每次新連線都有相同選項。測試除了讀取 `PRAGMA foreign_keys` 的值，也要實際插入一筆無效外鍵資料，確認資料庫拒絕，而不是只相信設定名稱。

## 交易與單一寫入者

SQLite 可以有多個讀取者，但同一時間的寫入仍受鎖定規則限制。對本機單管理員部落格，保守的小型連線池通常足夠；盲目增加連線數不會增加寫入能力，反而可能增加競爭。

busy_timeout 讓短暫鎖定有等待的機會，但它不會修復過長交易。不要在開啟交易後呼叫慢速外部服務，或等待使用者確認。資料檢查與寫入應在可預期的時間內完成。

## 明確 DDL 比猜測更容易審查

使用固定 SQL 建表與索引，可以直接看見欄位型別、CHECK、UNIQUE 與刪除規則。JPA 映射必須和 SQL 對齊；不要同時啟用 Hibernate create-drop，又執行自己的 schema 初始化，否則重啟可能清空資料或發生互相衝突。

文章刪除時，post_tags 的關聯列可以連帶清除，標籤本身則保留。分類仍被使用時應拒絕刪除。資料庫外鍵提供最後防線，Service 則在操作前給出使用者能理解的提示。

備份時要考慮資料庫與 uploads 目錄是一組資料。簡單本機部署可以先停止程式再複製整個資料目錄，避免只複製 DB 卻漏掉圖片。若未來需要線上備份，應另行設計一致的快照流程，不能假設複製一個正在寫入的檔案永遠安全。
