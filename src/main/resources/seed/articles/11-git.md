## 審查者看到的是差異

一個提交最好回答一個具體問題：修正什麼情境、改變什麼行為、如何驗證。若同時混入格式化、功能新增與資料檔案，審查者很難辨認重要變更。小而完整的提交不是追求行數少，而是讓變更可以獨立理解。

```text
git status --short
git diff
git diff --cached
```

工作目錄差異與暫存區差異不同。提交前應看 staged diff，因為真正會提交的是暫存區內容，而不是編輯器目前開著的檔案。選擇性加入檔案能避免把執行期產物一併送出。

## .gitignore 不是秘密管理系統

SQLite DB、上傳圖片、target、私人 IDE 設定與 .env 應排除在原始碼版本之外。已經被追蹤的檔案，不會因為新增 gitignore 規則就自動消失。若秘密曾經提交，需要依情境撤銷與更換，不能只刪除目前版本就當作解決。

示範圖片與初始化文章是專案必要資源，應放在 resources 中追蹤；使用者執行後上傳的圖片則屬於資料。兩者即使都是 PNG，也有不同的交付責任。

## 提交訊息描述可觀察行為

相比「update files」，「修正撤回文章後仍可讀取圖片」更容易理解。本文還可交代具體觸發條件、修改方式與測試結果。若只是調整一段文案，不必硬塞冗長模板；資訊量應和風險相稱。

在協作前，也應確認工作目錄是否已有使用者的未提交變更。自動工具不應為了取得乾淨狀態直接覆寫或清除他人的工作。必要時先隔離改動，並明確報告衝突。

## 把交付和提交分開

專案可以先準備完整原始碼、README、測試報告與獨立 JAR，讓使用者決定何時建立提交、上傳 GitHub 或寄送面試作品。能建置不代表已獲授權發布，開發完成也不等於需要自動推送。

一份好的交付說明應讓接手的人找到入口：需求文件在哪裡、分層如何安排、如何執行測試、資料放在哪裡，以及有哪些實際限制。這些內容往往比漂亮但無法重現的展示更有審查價值。
