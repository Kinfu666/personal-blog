## 先列出需要被保護的行為

整合測試的重點是驗證多個元件協作後的結果。對 SQLite 部落格而言，外鍵是否啟用、交易是否回滾、Session 與 CSRF 是否一起工作，都不是只靠 mock Repository 就能確定的事情。測試應從需求的可觀察結果出發。

```java
@DynamicPropertySource
static void database(DynamicPropertyRegistry registry) throws IOException {
    Path directory = Files.createTempDirectory("blog-test-");
    registry.add("app.data-dir", directory::toString);
}
```

每個測試情境使用獨立的暫存 SQLite 檔案，避免開發資料被測試清掉，也避免測試之間共享隱藏狀態。若要依靠交易自動回滾，要理解 Web 請求是否真的使用同一個交易；真正的 HTTP 伺服器通常在不同執行緒工作。

## 讓負向測試驗證拒絕的原因

插入無效外鍵應檢查 SQLite 確實拒絕約束，而不只是捕捉任意例外。否則 SQL 拼錯或連線失敗也可能讓測試誤判成功。圖片驗證也應同時涵蓋有效 PNG、JPEG、WebP，避免一個「全部拒絕」的錯誤實作通過所有負向案例。

Markdown 可用純單元測試快速驗證，因為它不需要資料庫。公開文章查詢則需要實際關聯與排序資料，應建立超過一頁且有相同發布時間的情境。不同層級的測試對應不同風險，不必把每個案例都啟動整個系統。

## 測試不能只重述實作

驗證方法被呼叫一次，不一定能證明使用者得到正確結果。更有價值的檢查是：草稿沒有出現在搜尋、無效表單保留標題、刪除文章不刪標籤、缺 CSRF 的寫入遭拒。

同時也不要把測試寫成應用程式的另一份實作。預期結果應小而明確，例如列出六個應出現的 ID，而不是再寫一個與正式程式完全一樣的查詢演算法。

交付前還需要真正啟動封裝好的 JAR。測試環境的 classpath、資源路徑和工作目錄可能與可執行封裝不同；只有從新目錄啟動、操作並重啟，才能驗證交付情境中的初始化與持久化。
