## 先描述查詢，再討論索引

公開首頁的主要查詢是：只列出 PUBLISHED，依 published_at 降冪，再依 id 降冪。索引應對應這個具體模式，而不是看到某個欄位就建立一個索引。複合索引的欄位順序會影響可使用的查詢前綴與排序能力。

```sql
CREATE INDEX idx_posts_published
ON posts(status, published_at DESC, id DESC);

EXPLAIN QUERY PLAN
SELECT id, title FROM posts
WHERE status = 'PUBLISHED'
ORDER BY published_at DESC, id DESC
LIMIT 6 OFFSET 0;
```

`EXPLAIN QUERY PLAN` 可以協助觀察是否使用索引，以及是否需要額外暫存排序。計畫會隨資料分布與資料庫版本改變，測試不宜把整段文字鎖死；應關注是否出現不合理的全表掃描與成本。

## 關聯表需要雙向思考

post_tags 的複合主鍵 `(post_id, tag_id)` 適合查詢某篇文章的標籤。若使用者反過來以 tag_id 篩選文章，就需要考慮 `(tag_id, post_id)` 索引。相同兩個欄位的不同順序，服務的是不同的查詢入口。

分類篩選可有 category_id 索引，但分類與發布排序合併時，最佳方案仍取決於資料量與選擇性。小型部落格不應為每個可能組合建立索引，因為索引也佔空間，並增加每次新增、更新與刪除的維護成本。

## 關鍵字搜尋有不同的限制

`LIKE '%keyword%'` 通常不能有效使用一般 B-tree 索引的前綴搜尋能力。這個小型專案可以接受掃描文字欄位；不能因為看見搜尋需求就未經規劃引入新的搜尋服務。未來若資料量增加，應先量測，再依既定規格討論專用全文索引。

使用者輸入中的 `%` 與 `_` 也要定義語意。若產品要的是字面關鍵字，這些字元應被跳脫，而不是偷偷變成 SQL 萬用字元。參數綁定負責避免注入，LIKE 跳脫則負責搜尋語意，兩者不能混為一談。

索引練習可以先建立幾千筆測試資料，記錄加索引前後的計畫與查詢時間，再移除不再需要的測試資料。不要把效能測試產物打包進真正的展示資料庫。
