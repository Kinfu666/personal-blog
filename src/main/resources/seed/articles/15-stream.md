## Stream 適合表達資料如何轉換

將標籤 Entity 轉成畫面使用的 NamedItem，是一個清楚的映射：輸入一筆資料、輸出一筆資料，沒有外部狀態變更。這類流程用 Stream 往往比建立清單再逐筆加入更直接。

```java
List<NamedItem> items = tags.stream()
    .sorted(Comparator.comparing(Tag::getName))
    .map(tag -> new NamedItem(tag.getId(), tag.getName()))
    .toList();
```

這裡的排序規則是資料契約的一部分。若使用者介面需要繁體中文特定排序，單純 Unicode 順序未必符合期待，應另行明確定義；不要在沒有需求時讓每一層自行選不同規則。

## 避免把副作用藏在 map 裡

map 應用來轉換值，不適合偷偷寫資料庫、修改另一個集合或刪除檔案。當操作有順序、補償或錯誤處理需求時，清楚的 for 迴圈通常更容易審查。文章初始化就是例子：每篇讀檔、替換圖片路徑、驗證、儲存，需要清楚看見失敗會停在哪裡。

`parallelStream()` 也不是免費加速。JPA EntityManager 與交易通常綁定執行緒，把延遲載入或寫入操作丟到平行 Stream，可能失去原交易脈絡。對小型後台，明確、穩定的執行順序比未量測的平行化更重要。

## 集合型別會透露需求

若標籤 ID 不得重複，可以使用 Set；若還需要保留使用者選擇順序，可考慮 LinkedHashSet。DTO 回傳不可修改的 List，能防止畫面程式意外改變服務層結果。選擇集合時，應先回答是否需要順序、唯一性與可修改性。

空集合應是正常結果，而不是 null。這讓模板與轉換流程不必額外區分「沒有標籤」與「集合不存在」。若資料庫回傳的結果不符合預期，則應在服務邊界提出明確錯誤，而不是讓 Stream 中途發生難讀的空值例外。

最後可以用一個簡單準則檢查可讀性：同事能否在不追蹤外部變數的情況下，讀懂每一個中間步驟？若答案是否定的，拆出有意義的方法或改回迴圈，通常比繼續串接更多操作更有效。
