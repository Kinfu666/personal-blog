## 長度正確，不代表可以儲存

標題不為空、摘要最多 300 字，是輸入形狀的限制；分類是否存在、名稱是否已被使用，則依賴系統當下的資料。把兩者混在 Controller 中，容易出現重複查詢與難以測試的分支。

Bean Validation 適合宣告可局部判定的欄位規則。繁體中文訊息能讓使用者知道需要修正什麼，而不是只看到技術例外。

```java
public class CategoryForm {
    @NotBlank(message = "請輸入分類名稱")
    @Size(max = 50, message = "名稱最多 50 字")
    private String name;
}
```

表單 setter 可先去掉前後空白，讓「只有空白」正確成為必填錯誤。文章 Markdown 內容則不宜任意 trim，因為縮排與換行可能影響語法。正規化規則應針對欄位意義決定。

## 商業驗證與資料庫約束一起工作

新增分類時，Service 先計算 normalizedName，使用 Locale.ROOT 轉為小寫，再檢查是否重複。資料庫仍保留 UNIQUE 約束，因為兩個請求可能同時通過前置查詢。前置檢查提供友善訊息，約束保護最終一致性，兩者用途不同。

文章儲存時也應重新查詢分類與標籤。使用者開著編輯器期間，另一個管理工作可能刪除了尚未被引用的標籤；表單送出的 ID 並不證明資料仍然存在。不能安靜忽略不存在的標籤，否則使用者以為儲存成功，實際內容卻被改變。

## 錯誤應回到可操作的位置

可修正的錯誤應放到對應欄位，例如 categoryId 的「分類不存在，請重新選擇」。文章標題與內容應原樣保留，避免使用者為一個分類錯誤重新輸入整篇文章。無法刪除仍被文章引用的分類，則適合在列表顯示操作結果。

測試可以同時涵蓋三層：直接驗證空白與邊界長度、呼叫 Service 驗證無效關聯與重複名稱、透過 MockMvc 確認失敗頁面保留輸入。不要只測表單上的 required 屬性，因為 HTTP 請求可以完全繞過瀏覽器驗證。

最後，錯誤日誌應提供排查線索，但不要把密碼、Session ID 或整份敏感表單直接記錄。可追蹤不等於把所有資料印出來。
